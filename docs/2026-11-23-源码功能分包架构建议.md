# PyTeXMK 源码功能分包架构建议

2026-11-23，面向当前 PyTeXMK 工作区。依据此前功能审查、现有模块清单与少量入口和资源路径核对编写。本次交付为目录重组建议。

建议将当前根目录的功能模块归入七个子包，沿用已有 `cli/`，新增 `project/`、`build/`、`artifacts/`、`reporting/`、`runtime/` 和 `ui/`。先以文件为单位迁移并直接更新调用方，后续再按维护需要拆分过大的文件。用户提出尽量避免薄层转发，因此迁移后每个模块只有一个实际位置，子包入口保持最小化。

目录树即完整迁移映射。现有 `cli/*.py` 保持当前文件名，根目录功能模块移到树中指定的子包并保留文件名。为每个新子包增加最小的 `__init__.py`。`data/`、`locale/` 和四个根入口或版本文件保持各自的资源与入口职责。

这套分类规模适合当前几十个模块。`build/compile_engine.py` 的完整导入路径能表达编译功能，`project/context.py` 能表达项目上下文。无需在同一轮将所有模块改名、引入更深层级或建立通用服务框架。

## 各包的职责与边界

| 包 | 负责的功能 | 后续改动的落点 |
| --- | --- | --- |
| `cli` | argparse、动作组合、配置到运行参数的适配、批量和监听工作流、最终退出 | `-r` 等 CLI 设计、参数作用域校验、编排和最终 JSON 发射时机 |
| `project` | 配置加载、项目根与工作目录身份、主文件及别名、魔法注释、扫描和静态预检 | 目标选择优先级、配置结构验证、静态路径误判 |
| `build` | 引擎参数、BibTeX/Biber 和索引调度、轮次收敛、依赖清单、缓存与辅助文件自愈 | 文献变更失效、轮次停止原因、产物发布后的状态提交 |
| `artifacts` | 投稿内容处理和归档、差异输入展开、PDF 工具与 SyncTeX 查询 | 投稿包完整性、差异文件保真、PDF 修复、定位配对检查 |
| `reporting` | PyTeXLogs 适配、诊断摘要、编译检测表、机器可读结果的组装 | 报告写盘状态、诊断来源、JSON 字段与批量结果表达 |
| `runtime` | 文件原子替换与回滚、子进程 I/O、冻结环境、临时目录、日志、计时、翻译和资源位置 | 管道收尾、进程回收、文件占用重试、资源发现 |
| `ui` | 控制台输出通道、Rich 主题、横幅和帮助用通用展示 | 控制台重定向和格式化。各功能特有的诊断文案仍随其功能维护 |

`fls.py` 和 `layout.py` 放在 `build/`，因为前者表达 TeX recorder 输入，后者表达构建产物和依赖后缀。投稿与 PDF 工具可以直接导入这两项共享构建知识。`file_ops.py` 放在 `runtime/`，提供可重用文件操作，其调用范围由具体功能决定。

`lifecycle.py` 放进 `cli/`，它当前负责进程退出及最后的机器结果输出。核心编译和产物处理逐步通过返回值或异常报告失败，退出码由外层决定。分包阶段先保留其现有调用语义，再单独修正批量 JSON 等行为。

`cli_context.py` 与 `project/context.py` 各自保留。前者把命令行参数、配置和魔法注释组合为工作流状态，后者表达项目目录与子项目身份。以后若抽取有效构建计划，优先从现有逻辑中移动真实决策，避免再叠加一个只传参数的类。

`cli_latexdiff.py` 负责命令行动作和收尾，`artifacts/latexdiff.py` 负责差异输入及工具行为。若现有函数只是原样转调，可在后续职责整理中直接合并到实际调用方或实现模块。文件名相似本身不足以证明需要新增中间层。

## 直接导入与依赖方向

内部调用直接导入符号的实际定义模块，例如以下形式。

```python
from pytexmk.build.build_state import BuildState
from pytexmk.project.context import ProjectContext
from pytexmk.runtime.file_ops import FileMoveRemoveManager
from pytexmk.runtime.language import set_language
```

同包内可用相对导入，跨分类包使用明确的绝对导入。每个子包 `__init__.py` 默认只放包说明，按确有用途导出少数公开符号。旧根路径的内部调用及测试直接更新至新位置。

目标依赖以 `cli` 编排功能为主。`project` 提供项目信息，`build` 执行构建，`artifacts` 可调用构建能力完成差异稿或投稿验证，`reporting` 处理构建结果与日志，`runtime` 和 `ui` 提供执行及展示能力。`build` 对 `artifacts` 的高层工作流保持克制，避免形成互相调度。

这是后续维护方向。当前编译、诊断和子进程代码已有 Rich 输出及生命周期调用，迁移目录时无需为追求层级纯度新增接口、依赖注入容器或通用基类。循环导入若因路径调整显现，先找具体反向调用，移动其真实职责或数据定义。保留有明确启动收益的局部导入。

现有根包启动、`python -m pytexmk.cli` 和控制台入口属于已使用的启动契约，可继续保持紧凑实现。`--version` 快速路径仍只加载版本所需内容，包级初始化避免导入全部功能。

现有 `pytexmk.__getattr__` 的惰性访问兼容若仍有使用者，迁移期间保留。只有确认存在外部调用契约时，才对具体旧路径提供限期兼容；普通内部模块移动后直接改引用。兼容代码明确列出旧路径、替代路径与移除条件，避免每个旧文件都留下转发壳。

## 需要同时处理的路径与工具耦合

### 翻译和资源定位

`language.py` 移到 `runtime/` 后，当前以 `Path(__file__).parent / "locale"` 定位资源的源码路径会改变。迁移时改为以 `pytexmk` 包资源为锚点，并核对冻结运行时 `_MEIPASS` 下的资源布局。`locale/` 本身继续放在根包，翻译域名称继续使用已有值。目录调整无需重建整套翻译域。 [现有定位](../src/pytexmk/language.py)

`paths.py` 当前已用 `importlib.resources.files("pytexmk")` 定位源码包根，迁移到子目录后该语义仍适用。`tools/lang_tool.py` 递归扫描 Python 文件并按 `set_language` 域分组，需验证迁移后的源文件仍被收集。 [资源路径](../src/pytexmk/paths.py) · [翻译工具](../tools/lang_tool.py)

### 打包与版本

`pyproject.toml` 的版本提取使用 `pytexmk.version.__version__`，因此 `version.py` 保留根位置有实际收益。setuptools 的包发现包含 `pytexmk*`，新子包需要自己的 `__init__.py`。配置模板和翻译资源继续按根包资源分发。PyInstaller 的 locale 数据目标和入口文件需逐项核对，动态导入中写死的模块字符串也需要更新。 [打包元数据](../pyproject.toml) · [冻结构建](../tools/pack.py)

### 测试和补丁目标

除了普通 import，测试中的 monkeypatch 字符串也要指向实际定义和使用位置。只改导入而保留旧补丁路径，可能造成测试在替身外调用真实工具。现有命令行、构建状态、PDF 修复和诊断测试需要一起更新。

测试重组可稍后按 `project/`、`build/`、`artifacts/`、`reporting/`、`runtime/`、`cli/` 和 `integration/` 对应组织。第一轮优先完成源码搬迁与测试导入更新，随后独立移动测试文件，便于识别收集配置和 fixture 作用域变化。

## 分阶段迁移

| 阶段 | 工作内容 | 验收重点 |
| --- | --- | --- |
| 0 | 保存当前工作区基线，列出所有源文件与目标路径，检查现有未提交修改 | 保留用户现有改动，按当前测试实测基线，不沿用旧报告通过数 |
| 1 | 迁移 `ui/` 与 `runtime/`，更新全部直接引用、补丁路径和资源定位 | 版本入口、帮助、输出重定向、翻译资源、文件回滚、子进程回收 |
| 2 | 迁移 `project/` 与 `build/`，更新导入与共享后缀和 recorder 的使用点 | 配置与目标身份、文献和索引调度、缓存、native Biber 的输入目录 |
| 3 | 迁移 `reporting/`、`artifacts/` 和 `lifecycle.py`，调整跨分类调用 | JSON 发射、报告路径、投稿、差异稿、PDF/SyncTeX 配对 |
| 4 | 更新现有架构文档与开发说明，验证 wheel 和冻结包 | 三个启动入口、资源完整性、真 TeX 构建、归档后跳转 |
| 后续独立轮次 | 从 `cli_compile.py` 等大模块提取真正的构建计划、产物发布和清理规则 | 每次提取要减少重复决策，并保留或补充行为回归 |

每一阶段开始前检查它与尚未迁移模块的互相导入，更新调用点后再运行测试。若阶段之间依赖过密，可以合并一次原子搬迁，避免为阶段拆分而新增临时转发模块。

每轮执行仓库规定的 Ruff、`compileall`、相关及全量 pytest、版本检查。入口或资源路径变化的轮次增加帮助、英语界面、一次正常 article 和一次 BibTeX/Biber 构建。最终验证冻结版入口及真实构建。对迁移前已复现的功能缺陷记录一致性，独立安排修复，方便审查目录调整是否引入新行为。 [修改约定](code-modification-playbook.md) · [功能审查及测试缺口](2026-11-23-功能审查与改进方案.md)

## 完成标准

迁移完成后，根包只承担启动、版本与资源锚点，各功能可从分类目录直接找到。内部导入、动态模块名和测试补丁均指向实际定义位置。新目录中每个文件包含明确实现，各包初始化保持小体量，公开入口与资源分发通过验证。

优先采用上述目录，继续沿用现有文件名。过大模块的职责提取、CLI 参数精简、缓存修复与文件保真修复按单独轮次推进。这样可以先获得可浏览的功能结构，再用已列出的回归场景检验后续架构调整。
